Docker layer

Why put a compliance check in a Docker image?

A script that only runs on one laptop is a demo. Building it into a Docker image is what turns it into a control that runs on its own — and what gets left out of that image is a security decision in itself.

01 The problem

Before Docker

The script

Reads live S3 config, grades it against three frameworks

One laptop

Depends on the Python and boto3 installed on that machine

Runs when you run it

Evidence is a point in time, gathered by hand

02 What Docker changes

After Docker

One Docker image

Script and its dependencies sealed into a single versioned unit

Any machine

Server, cluster, or cloud runner — behaves identically

On a schedule

Evidence collected continuously, with nobody in the loop

That last step is the point. A control checked once by hand is a screenshot with extra steps. A control checked every day on its own is continuous monitoring — and because the image is versioned, the evidence produced last quarter traces back to an exact build.

03 What the image build decided

Running this anywhere other than one laptop means shipping an environment with it. The only real question was how much environment to bring — and each answer in the Dockerfile maps to a control.

47.2 MB against roughly 1 GB for a standard python:3.12 base The script is a few kilobytes either way. Everything else that travels with it has to be patched and scanned, whether the script uses it or not.

Chainguard distroless base

No shell and no package manager, so nothing can be installed into a running container and common payloads that call a shell simply fail.

NIST CM-7

Multi-stage build

pip and the build stage never reach the shipped image. Only the interpreter, boto3, and the app code ship.

NIST CM-7

Runs as a normal user

Declared explicitly in the Dockerfile rather than inherited, so the privilege decision is visible to anyone reviewing it.

NIST AC-6 · SOC 2 CC6.1

No credentials in the image

AWS identity is mounted read-only when the container runs. Anyone who obtains the image gets no access to the account.

NIST IA-5

04 Build and run

# build the image
docker build -t grc-evidence-collector .
 
# identity is mounted at run time, never baked in
docker run --rm -v "${HOME}/.aws:/home/nonroot/.aws:ro" grc-evidence-collector

Known limitations and the production identity path are documented in the repository README.
